# C/C++ to x64 Assembly migration completion

Milestone: `voodka-port-v1.2.0`
Completion date: 2026-08-12

## Final boundary

The shipped Windows demo is `port/bin/<Config>/VOODKA.exe`. It is a native
PE32+ GUI image whose entry point, demo core, Win32 host, window procedure,
input watcher, arena/archive services, logger, timer, timeline recorder,
application coordinator, D3D11 presenter, WASAPI worker, tracker, mixer,
shutdown path, and scene modules are NASM x64.

`VOODKA.exe` does not link C++ objects, the MSVC CRT/STL/exception runtime,
libxmp, or a compiler startup object. It contains only a small freestanding C
XZ decoder alongside the NASM image. Its only runtime dependencies
are Windows system DLLs used by the assembly platform layer: Kernel32,
User32, GDI32, Ole32, DXGI, D3D11, and the normal graphics/audio driver
stack. The production import audit rejects CRT, libxmp, and unexpected
third-party imports.

The C++ graph is intentionally retained outside the shipped image:
`VOODKA_REFERENCE.exe` is the C++/libxmp behavioral oracle, while packers,
asset viewers, self-tests, and CTest probes are host-side validation tools.
This is deliberate test infrastructure, not a compatibility layer used by
the demo.

## Build and package

From `port/`:

```powershell
.\build.ps1 -Clean -Config Debug -Test
.\build.ps1 -Clean -Config Release -Test
.\verify_production.ps1 -Config Release -RunTests -PackageRun -FullRun
```

`build.ps1` locates the Visual Studio x64 environment, configures CMake with
the vendored NASM 2.16.03 compiler and Python 3 compressor, builds
`port/bin/<Config>/`, embeds one deterministic XZ/LZMA2 VPK1 payload, and runs
the CTest matrix when `-Test` is selected. The release package contains only:

```
VOODKA.exe
```

The archive is generated by the original Pascal linker semantics through
`vodka_pack`; the 1000-entry offset table and 76 `VODKA.TXT` indices are
preserved. Build-time `compress_assets.py` stores the archive and module as
two XZ/LZMA2 streams using one decoder implementation. The production arena
loader and audio service decode directly into their final runtime buffers.
The original source, release binary, and recovered palette/object provenance
under `reference/` remain read-only.

## Runtime architecture

The assembly modules are organized by ownership:

- `core/boot.asm`, `core/parts/`, and the scene includes contain the
  migrated demo and eight scene entry points.
- `core/eos_replace/eos_dispatch.asm` translates EOS service IDs into the
  native Windows service ABI; `win32_arena.asm` owns the single 64 MiB
  arena and archive loading.
- `win32_app_entry.asm`, `win32_app_host.asm`, `win32_app_window.asm`,
  `win32_app_wndproc.asm`, and `win32_input.asm` own process startup,
  command-line parsing, the window, focus, keyboard state, ESC, and close
  messages.
- `win32_app_startup.asm`, `win32_app_modes.asm`, and
  `win32_shutdown.asm` own subsystem order, scene selectors, rollback, and
  idempotent teardown.
- `timer.asm`, `win32_log.asm`, `win32_timeline.asm`, and the bridge
  adapters provide QPC pacing, logging, A/V records, and the decorated
  namespace ABI.
- `win32_d3d_dispatch.asm` and `d3d11_asm_present.asm` create the D3D11
  device and palette/indexed presenter. The 320x200 indexed framebuffer is
  point-sampled to the default 1280x800 window or the opt-in
  `--fullscreen-1920x1080` borderless output. At 1920x1080 the centered image
  is 1600x1000 at integer 5x scale and the remaining area is pure black;
  palette values are expanded from VGA 6-bit components to 8-bit shader values.
- `audio_mod.asm`, `audio_tracker.asm`, `audio_event.asm`,
  `audio_effects.asm`, `audio_voice.asm`, `audio_pcm.asm`,
  `audio_workers.asm`, and the audio controller/ring modules implement
  the 14-channel FastTracker player, 44.1 kHz stereo PCM mixer, synchronization
  markers, pause/seek state, and event-driven WASAPI output.
- The VR/world modules load the packed V3D/V3M records, camera paths,
  palettes, texture records, water tables, and scene-specific object
  instances without a C++ renderer.

All NASM-to-Windows calls follow the Win64 ABI. The stack is 16-byte aligned
at every call instruction, nonvolatile registers are preserved, and 32-bit
archive/arena offsets are explicitly based by the qword `Code32_addr`.

`--modpos`, `--order`, and `--ms` seek the soundtrack timeline.
ModPos is `(order << 8) | row`. Space pauses/resumes both clocks; ESC and
the title-bar close request the same process-wide teardown from any scene,
loading state, or playback position. `--record` captures indexed frames and
palettes, and `--timeline` captures frame, ModPos, and audio-clock evidence.

## Migration history

The repository keeps the migration ledger in
`ASSEMBLY_MIGRATION_PLAN.md` and the dated Phase 0-3 records. In summary:

1. The original TASM/EOS DOS source and shipped release were preserved as
   read-only provenance.
2. The NASM x64 core and data/asset pipeline were made relocatable and
   validated against the original scene formats and captures.
3. D3D11/COM presentation, the dedicated tracker/mixer/WASAPI path, and the
   complete Win32 process/window/thread lifecycle were moved behind native
   assembly ABIs.
4. The C++ implementation was isolated as a differential oracle and the
   host validation matrix was expanded to cover ABI contracts, scene
   rendering, asset formats, audio state/PCM, synchronization, shutdown,
   and import hygiene.
5. The final clean Debug and Release gates, packaged full-demo run, A/V
   timeline, scene progression, and ESC/window-close probes authorize this
   milestone tag.

The dated phase documents intentionally retain earlier implementation wording
so the route to the final architecture remains auditable. Their opening
status blocks point back to this completion record.
