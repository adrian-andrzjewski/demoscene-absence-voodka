# Phase 1 progress: D3D11/COM assembly feasibility gate

Status: **Phase 1B and Phase 1C passed; G1 is passed and the shipped target
now uses assembly-owned D3D11/COM presentation.**

The assembly-only application is not claimed yet. Window management, input,
timing, audio, logging, lifecycle, and the remaining C++ platform code are
still present. The complete C++ presenter remains compiled only in the
non-shipped `VOODKA_REFERENCE.exe` behavioral oracle.

Snapshot date: **2026-08-10**

## Gate structure

Phase 1 was ordered from the riskiest interoperability proof to the real
production path:

1. **Phase 1A:** direct NASM calls into D3D11, DXGI, and COM vtables.
2. **Phase 1B:** a complete NASM-owned indexed/palette presenter with GPU
   readback and Present.
3. **Phase 1C production ownership:** `VOODKA.exe` defaults to the NASM
   presenter and no longer compiles the C++ D3D11 implementation; the
   reference executable retains the C++ path and `--asm-present` comparison.

The C++ side still creates the HWND, pumps messages, owns diagnostic files, and
selects the presenter. It does not create or manipulate a D3D11 object when
`--asm-present` is selected.

## Phase 1A: direct D3D11/COM proof

The validation target is:

- NASM implementation: [`d3d11_asm_probe.asm`](../port/core/eos_replace/d3d11_asm_probe.asm)
- C++ host: [`d3d11_asm_probe.cpp`](../port/tools/validate/d3d11_asm_probe.cpp)
- CTest name: `d3d11.asm_probe`

The C++ host creates a hidden HWND and initializes the COM apartment. NASM
directly performs:

1. `D3D11CreateDeviceAndSwapChain` with an explicit Win64 stack argument area;
2. `IDXGISwapChain::GetBuffer` through vtable slot 9;
3. `ID3D11Device::CreateRenderTargetView` through slot 9;
4. `ID3D11DeviceContext::OMSetRenderTargets` through slot 33;
5. `ID3D11DeviceContext::ClearRenderTargetView` through slot 50;
6. `ID3D11Device::CreateTexture2D` for a staging texture through slot 5;
7. `ID3D11DeviceContext::CopyResource`, `Map`, and `Unmap` through slots 47,
   14, and 15;
8. `IDXGISwapChain::Present` through slot 8; and
9. `IUnknown::Release` for every acquired interface.

The staging readback checks a real GPU result. The probe clears an
R8G8B8A8 target to `(1.0, 0.25, 0.5, 1.0)` and verifies the returned pixel
bytes, feature level, and row pitch.

## Phase 1B implementation

The production candidate is:

- NASM implementation: [`d3d11_asm_present.asm`](../port/core/eos_replace/d3d11_asm_present.asm)
- Standalone C++ host: [`d3d11_asm_present_probe.cpp`](../port/tools/validate/d3d11_asm_present_probe.cpp)
- Build-time shader compiler: [`d3d11_shader_compile.cpp`](../port/tools/validate/d3d11_shader_compile.cpp)
- CTest name: `d3d11.asm_present_probe`
- Runtime selector: `VOODKA.exe --asm-present`

The candidate exports these actual interfaces:

```text
asm_present_init(hwnd, width, height) -> uint32_t status
asm_present_set_palette(rgb6_interleaved_768_bytes)
asm_present_draw(arena_base, framebuffer_offset) -> uint32_t status
asm_present_readback(out_rgba8, capacity) -> uint32_t status
asm_present_present() -> int32_t HRESULT
asm_present_shutdown()
```

NASM owns all D3D11 resources and operations:

- device, context, swap chain, back buffer, and render-target view;
- dynamic 320x200 R8 indexed texture and 256x1 RGBA palette texture;
- shader-resource views, input layout, fullscreen vertex buffer, and embedded
  precompiled vertex/pixel shader bytecode;
- point/clamp sampler, unc culled rasterizer, and staging readback texture;
- row-pitch-aware texture uploads and readback;
- palette conversion `(value * 255 + 31) / 63`;
- fullscreen draw, Present, and partial-initialization/shutdown Release calls.

The host-side shader compiler is a build tool only. Its generated bytecode is
embedded into the assembly object; runtime `D3DCompile` is not part of the
assembly presenter.

## Defects found and fixed

The feasibility work found concrete ABI and API hazards rather than merely
proving object creation:

- D3D creation stack arguments were initially placed at the callee offsets;
  the caller-side fifth argument is `[rsp+0x20]` before `CALL`.
- Device vtable slot counting corrected `CreateRenderTargetView` to slot 9
  and `CreatePixelShader` to slot 15.
- Context slots were corrected for `Map`, `Unmap`, resource binding, viewport,
  clear, copy, and draw calls.
- `D3D11_MAP_WRITE_DISCARD` is value 4, and
  `D3D11_BIND_VERTEX_BUFFER` is `0x1`.
- Map stack arguments were given a frame large enough not to overwrite saved
  nonvolatile registers.
- Mapped `RowPitch` is a 32-bit field and is handled as such.
- The sampler and rasterizer output pointers use the correct register for
  their two-argument device calls.
- Viewport width and height are IEEE-754 `FLOAT` fields, not integer fields.
- The render target is explicitly cleared before drawing, matching the C++
  reference path.
- Hidden-window `Present` may return `DXGI_STATUS_OCCLUDED` (`0x087A0001`);
  the probe validates the call while accepting that expected diagnostic-window
  status. A visible application window uses the normal successful path.

These failures justify keeping the shared [`win64_abi.inc`](../port/core/inc/win64_abi.inc)
contract and the executable probes in the repository.

## Milestone decision

**GO for Phase 2 audio feasibility and the later platform conversion.** Native
x64 assembly can reliably interoperate with the current D3D11/COM renderer,
preserve the indexed/palette visual output, and carry a full demo playback.

**NO-GO for claiming 100% assembly.** The C++ presenter is now reference-only
for the shipped target, but the production dispatch still contains host-side
recording and diagnostic file I/O. Window management, input, timing, audio,
logging, lifecycle, and the remaining C++ platform code still require their
own gates.

## Phase 1C result: assembly presenter is the shipped default

Phase 1C makes the D3D11 ownership split structural:

- `VOODKA.exe` compiles `d3d11_dispatch.cpp`, which calls only the NASM
  presenter ABI and retains host-side recording/diagnostic file handling;
- `VOODKA.exe` does not compile `d3d11_present.cpp`;
- `VOODKA_REFERENCE.exe` retains `d3d11_present.cpp` as the C++ visual oracle;
- a normal production launch selects the assembly presenter without a flag;
  `--asm-present` remains a compatibility alias; and
- the NASM presenter remains responsible for D3D11/COM creation, vtable calls,
  texture uploads, shader/resource binding, readback, Present, and Release.

is not a GO for removing the remaining C++ application/lifecycle layer or for
claiming that the executable is already 100% assembly.
